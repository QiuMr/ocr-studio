## 推理核心完成 + 精度对齐（2026-10-21 晚）
- **37 个测试全绿**：33 单测 + pipeline_match（全流程基线）+ 3 个 tensor_diff。
  pipeline_match：文本不一致 0 / 框偏差>2px 0 / 置信度偏差>0.05 0。
- ort 2.0.0-rc.15 必须用 `load-dynamic`（本机无 .lib），加 `api-24` + `directml`。
- **三个 OpenCV/pyclipper 对齐坑（全部实证，非猜测，都有锁定测试）**：
  1. `cv2.resize`：横向 11bit 定点 + 纵向截断的两段式实现，系统性偏低 1 LSB。
     复刻后不一致从 4.0% → 0.12%；残差只剩首/末行（OpenCV 内部 SIMD 路径，无法外部还原）。
  2. `cv2.warpPerspective`：整数坐标=像素中心；源坐标量化到 1/32；越界逐 tap 补 0。
     复刻后 0/3069 逐位一致。
  3. `pyclipper` 整数语义（**最后一道缺口**）：输入坐标截断成整数、距离保持 double、
     输出坐标 half-up 四舍五入。纯浮点外扩会让框小 0.27px → 裁剪图 32x30 而非 33x31
     → 误检框置信度差 0.146。修复后 #6 置信度 Rust 0.748 vs Python 0.748。
- **精度问题的定位方法论（值得复用）**：逐层排除——输入张量(加 LSB 敏感性测试) →
  EP(CPU vs DML) → 优化级别(BASIC/EXTENDED/ALL) → 推理(rec_probe 喂同一张量) →
  预处理 → 最后才落到 det 框的全精度值上。**整数取整后的框比对会掩盖亚像素差异**，
  必须打全精度。
- **生产隐患**：system32 里有 onnxruntime.dll 1.17.1（低于 ort 要求的 1.24.x），

- **前端技术栈改为 React + TS + Tailwind + shadcn/ui**（2026-10-21 用户确定），

**两个真 bug（都是自己写的时候没意识到）**
1. **坐标系不配对**：`window_rect()` 用 `ClientToScreen`+`GetClientRect` 拿客户区尺寸，
   却配 `GetWindowDC`（原点=窗口左上角，含边框）截图 → 右侧/底部缺一块。
   改 `GetWindowRect` 后自洽，实测 1455×941 与窗口矩形完全一致。
2. **粗筛度量选错**：原设计「SQDIFF 积分图粗筛 + NCC 精算」，理由是 SQDIFF 能 O(1)。
   **这个前提是错的** —— SQDIFF 的 `ΣT²+ΣI²-2ΣTI` 里 `ΣTI` 必须逐像素乘，
   和 NCC 一样是 O(tw·th)。代价相同就没必要用它对亮度敏感。
   实测模板 ×0.8 后真位置掉出 top-64 候选，直接漏检。改为全流程 NCC。

**性能（1080p 全屏 + 64px 模板）**
- debug 380ms → **release 60ms**（截图 30 + 匹配 30）；传图路径 31ms。
- 粗扫原 debug 424ms → 38.5ms。三招：`dot()` 内层改切片 zip；
  `from_rgb` 用 `chunks_exact(3)`；`MIN_TPL_SIDE` 8→6 让模板多降一层（位置数/4 × 面积/4）。

**踩坑**
- **手动跑 `cargo build` 的 exe 必须把 `runtime/*.dll` 拷到 exe 旁边**，否则
  `DmlExecutionProvider` 注册失败（"DirectML is not supported in this build of
  ONNX Runtime"）并**静默退回 CPU**。onnxruntime.dll 虽是绝对路径加载，但它依赖的
  DirectML.dll 仍按标准 DLL 搜索顺序找。打包产物由 `bundle.resources` 自动处理。
- Python `urllib` 走系统代理，访问 127.0.0.1 会拿到 **502**，别误判成服务没起来。
  用 `urllib.request.build_opener(ProxyHandler({}))` 绕开。
- `Start-Process` 起的 exe 会被 PowerShell 工具会话回收；要用 `run_in_background`。
- lucide-react 没有 `Window` 图标，用 `AppWindow`。

**测试**：40 单测 + 13 api_smoke + 16 重量级（含 5 个 capture_live）全绿。

## 2026-10-21 深夜：界面白屏根因修复（用户报「界面上什么都没有」）

**根因（一句话）**：`Cargo.toml` 的 `tauri = { features = [] }` 少了 **`custom-protocol`**。
这个 feature 决定 `generate_context!` 是否把 `frontendDist` 嵌进二进制；
没开时**连 `--release` 也走开发模式**，窗口去加载 `build.devUrl`（http://localhost:1420），
用户双击只能看到纯白或「localhost 拒绝连接」。`pnpm tauri build` 会自动带，裸 `cargo build` 不会。
→ 已改成 unconditionally 开启（dev 模式仍走 devUrl，不受影响）。

**排查链路（可复用的方法论）**
1. 先证明前端没问题：`python -m http.server` 托管 dist + Edge 无头截图 → 渲染完整。
2. 再看 App 进程状态：`Get-CimInstance Win32_Process -Filter "ParentProcessId=<pid>"` = **0 个 WebView2 子进程**
   → 不是「页面空」，是「视图没起来」。
3. Chromium 自带日志：wry 会覆盖 `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS`，
   必须从代码里 `additional_browser_args()` 传 `--enable-logging --log-file=... --v=1`。
   日志里直接给到两条铁证：
   - `FATAL:gpu_data_manager_impl_private.cc:408] GPU process isn't usable. Goodbye.`（GPU 进程 exit_code=7 连崩 6 次）
   - 页面 URL 是 `localhost:1420` → 立刻锁定 custom-protocol。
4. Crashpad 转储能查崩溃模块：写了零依赖 `scripts/minidump_info.py`（MDMP 头 → ModuleList(4)/Exception(6)，
   **MINIDUMP_MODULE 的 ModuleNameRva 在偏移 20**，不是 16）。

**顺带修的**
- 主窗口改为运行时创建（`tauri.conf.json` 的 `windows` 留空）：只有这样才能从代码传
  `additional_browser_args`，否则诊断参数根本进不去。
- 白屏看门狗：前端挂载后 `invoke("ui_ready")`，后端 10s 没收到就判定 WebView 已死，
  销毁并用 `--disable-gpu-compositing` 重建 + 写 `webview_compat=true` 持久化。
  （GPU 崩时 JS 一行都不执行，所以「有没有报到」是最可靠的判据。）
- 建窗失败也要降级重试：否则没有窗口 → Tauri 事件循环立刻退出（表现为「双击闪一下就没了」）。
- **release 是 GUI 子系统，没控制台 = 没日志**：加了文件日志 `<app_data_dir>/ocr-studio.log`
  （>8MB 自动清空）。白屏类问题以后有据可查。
- **`data_dir()` 是坑**：它返回 Roaming 根目录，`config.json` 会直接落到
  `C:\Users\xxx\AppData\Roaming\` 污染用户目录。要用 **`app_data_dir()`**（= Roaming\<identifier>）。
  已把 lib.rs 与 api/mod.rs 都改掉。清理前误放的 `%APPDATA%\ocr-studio.log` 被 safe-delete 拦了，未删。

**验收**：资源管理器启动 `D:\rust-target\release\ocr-studio.exe`，
