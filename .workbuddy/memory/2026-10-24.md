### 三个坑（都花过一次死路）

1. **SLANet 的 pad 填 0，不是 127.5**。paddlex 的 `Pad(val=127.5)` 套上去会输出
   500 个 `colspan` 垃圾 token；PaddleOCR 的 `PaddingTableImage` 才是 zeros。
   顺序也对：resize 长边 488 → **归一化** → pad 成 488×488 → CHW。
2. **bbox 两轴都乘 `max(宽,高)`**。图 pad 成方形，输出坐标相对方形；按「x 乘宽、
   y 乘高」得到压扁的框（实测 y 只有真实值的一半）。
3. **PicoDet 的分数已经是概率，不要再 sigmoid**。再套一层把背景的 0 变成 0.50 →
   detect 返回 **4093 个框** → auto 模式挨个识别 → 六核满载 **3500 CPU 秒**、
   请求永不返回。现象只有「界面一直转圈」，日志里连错误都没有，最难查的一次。

### 已知限制

- SLANet 输出的位置数有限（实测算到 19/32 位置），**单元格太多的表会被截断**，

## 并发摸底 + 至强 E5 崩溃问题排查

用户问两件事：① API 并发做得怎么样；② 别人家的 OCR 程序在至强 E5 上多线程并发闪退，
要不要针对这种处理器优化，我们有没有同样问题。

**新增 `scripts/verify_concurrency.py`**（并发验收）：
- 串行基线 → 1/2/4/8/16/32/64/200 并发阶梯，`--burst N` 单档、`--mixed` 混打五个端点
  （duohangjson/quyuocr/danzijson/shibie/zhaozi）查锁序死锁。
- 判定口径：结果**指纹**（文本+全精度框坐标）必须与串行基线一致 → 查串扰；
  后台 psutil 采样线程数/工作集 → 查线程与内存爆炸。`--proc` 要传对进程名
  （cargo 产物是 `ocr-studio`，分发包是 `OCR Studio`），否则线程数列 0。
- 踩坑：`/ocr/shibie` 返回 `{text,boxes}` 不是 `{rows}`，指纹函数一开始取错字段 →
  7 行识别被当成 0 行、指纹恒为 sha256("")。改用 `/ocr/duohangjson` 并把嵌套 box 展平。
  psutil 7 的 `memory_info()` 没有 `working_set`，要 `memory_full_info()`。

**实测结论**（release + DirectML + 12 逻辑核）：
- 200 并发全部成功、无串扰、进程不崩；峰值线程 60→72（仅 +12），内存 +50MB。
- 吞吐 3.8 张/s 封顶（全局互斥锁串行），延迟线性排队（200 并发最大 52.7s）。
- `OMP_NUM_THREADS=4` 完全无效 → 调 intra_op 线程数这条路实测否决。
- 空闲 CPU 0%，线程不空转。

**至强 E5 崩溃的成因判定**（对照我们自己代码）：
1. 共享 Session 并发 `run()` —— ORT 未定义行为，官方推荐解法就是「一个会话 + 互斥锁/队列」，
   **我们正是这个形态**（每模型建一次会话，全程复用）→ 没有这个问题。
2. 每请求/每线程各建一份 Session → 每份都开一整套线程池，多核至强上线程爆炸。
   我们会话只在加载时建一次 → 没有这个问题。
3. 老 E5（v1/v2，Sandy/Ivy Bridge，无 AVX2）→ onnxruntime ≥1.18 的 Windows x64 预编译包
   以 AVX2 为基线，Session 构造时 0xC000001D 静默退出。我们这份 DLL 是 1.24，**同类风险存在**，
   但本机没有 pre-AVX2 CPU 无法复现；且 ORT 的 MLAS 计算内核是按 CPUID 逐 ISA 分发的，
   真正裸跑 AVX2 的只是 Eigen/protobuf/会话装配那部分非分发代码。E5 v3（2014 Haswell）起都有 AVX2。

**待用户确认的优化清单**（任务 #123）：
A. 并发上限 + 快速失败（Semaphore，超出 429/503 + Retry-After）
B. 启动时 AVX2 检查 + 人话报错（防老 E5 静默闪退）
C. `decode_image` 加像素数上限（防 32MB body 解出 300MB 位图把进程拖到 OOM）
D. 会话池（可选配置，默认关）—— 工程代价大，仅当用户要多机吞吐
E. 换 `--cpu-baseline v1` 的 ORT DLL —— 要自己编 ORT，成本极高，已决定不做
F. 调 intra_op 线程数 —— 实测无效，已决定不做
