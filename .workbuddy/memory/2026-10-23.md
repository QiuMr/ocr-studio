## #87–#94 中文找图 + AI 操控服务（用户：「语义找图只能用英文？没法用中文吗」）

### 中文为什么不能直接喂文本塔（原理性，非工程懒惰）
MobileCLIP2-B 是 CLIP 英文语义空间：中文被 BPE 拆成 UTF-8 字节片。
实测 19 个常见中文词只有「人」偶然撞中（0.569，英文的 62%），其余全 0。
换中文文本塔不可行——特征空间与 YOLOE texthead 不对齐。

两条工程路子（都做了）：
- **词典** `engine/zh_words.rs`：内置中英词表（COCO 80 + 常用 UI 词）+
  `models/yoloe/zh_words.json` 用户覆盖。命中→映射英文进文本塔，类名回显中文；
  查不到→400 带相近中文词建议。
- **中文参考库** `engine/prompt_refs.rs`：框一次起中文名 → 走 VPE 图找图通道，
  不依赖 242MB 文本塔。存 `<数据目录>/prompt_refs/`（整张参考图，不裁小块）。

### 架构教训（本轮最重要，动引擎层前必读）
**`prompt.rs::text_pe` 必须保持纯净，中文映射只能放 API 边界的 `pe_for_words`。**
`text_pe` 是官方文本塔的逐位复刻——`yoloe_prompt_parity` 拿它对着 TorchScript
抠数值，而**基线夹具的 words 里故意混了中文词「确认按钮」**（测的就是官方
byte-token 行为）。一开始把词典解析加进 `text_pe`，parity 直接 FAILED。
分层后 parity 3/3 全绿。

### AI 操控服务（`api/ai.rs` + `api/ai_tools.rs`，复用 8848）
- 19 个工具：状态/清单/引擎/配置/日志/目标/截屏/认字/找词/找图/扫码/教目标/
  启停服务/改端口/改级别/改设备/改阈值。三风险档 readonly/write/dangerous。
- 信封 `{ok, summary, data, error}`：消费者是大模型，`summary` 是转述用户的人话，
  `error` 必须告诉 AI 下一步怎么做。
- Bearer 连接码（FNV 哈希混时间/pid/序号/ASLR 地址，不引 rand）+ 常数时间比较；
  `request_id` 幂等（回放 200 条 + inflight 占位，键用 `\x00` 分隔防撞键）；
  120 次/分钟滑动窗口限流；写操作审计日志。
- `closest_tool`：AI 写错工具名时给最接近候选（前缀优先，其次编辑距离 ≤3）。
- **刻意不进 `routes.rs` 的 `PATHS`**：那张表是「用户脚本能用哪些接口」的清单，
  AI 入口混进去会污染接口文档页。`/ai/v1/*` 默认关，403 文案指路「设置 → AI 控制」。
- 设置页「AI 控制」面板：开关/地址/连接码（复制/重置）/一键复制提示词/已教目标列表。

### 端点计数口径
`/vision/promptref` 一个路径三种方法：后端 `PATHS` 按路径算 19，
前端 `ENDPOINT_PATH_COUNT`（`new Set(paths).size`）对齐——不能取 `ENDPOINTS.length`。

### 收尾修的真问题（打包验收跑出来的）
1. **`DELETE /vision/promptref` 只认 JSON body**：`curl -X DELETE "...?name=中文"`

## 21:20 版本控制与自动更新（用户问「没有服务器怎么做版本控制、用户能自动升级吗」）

### 结论先给
两件事必须分开答：**代码别丢** 用托管仓库；**用户能升级** 用 Release 托管包 +
程序自己比对版本。用户原本想的蓝奏云不行——免费单文件 **100MB**，分发包 224.6MB。

### 仓库
`github.com/QiuMr/ocr-studio`（**public**，刻意选的）。34 提交 / `.git` 15MB /
最大文件 1.67MB → **不需要 Git LFS**。
公开的真正原因不是「想开源」，而是 **Release 资产匿名可下载**：私有仓库拉资产要 token，
程序自己拿不到，自动更新就只能退化成「给你个链接去下」。
配套加了 `.gitattributes`：`*.ps1 -text`（本机 `core.autocrlf=true`，`.ps1` 必须
BOM+CRLF，让 git 一字节都别碰）；源码实测本来就是 LF，不会产生 renormalize 噪音。

### 版本号收敛（这次最关键的结构性改动）
原来 `0.1.0` 硬编码在 **3 处**：`package.json`、`tauri.conf.json`、`pack_exe.ps1`。
漏改任一处都会让 zip 名和程序内版本对不上——用户报版本号时两边说的不是一回事。
现在只认 `tauri.conf.json`：
- `build.rs` 读出来 → `cargo:rustc-env=OCR_STUDIO_VERSION` → `version.rs::VERSION`
  （**不用** `CARGO_PKG_VERSION`，那是 Cargo.toml 的，天生会漂）
- `pack_exe.ps1` / `release.ps1` 用正则读同一个文件
- `/ocr/health` 新增 `version` 字段，脚本也能据此判断适配版本

### 为什么不用 tauri-plugin-updater
它只认**安装器**（NSIS/MSI）产出的签名包。本项目 `bundle.active = false` 发免安装 zip，
硬套会在「找不到安装器」和「已是最新」之间反复。**这个结论要记住，别再试官方插件。**

### 自研更新流程（`src/updater.rs`）
`releases/latest/download/latest.json`（固定资产路径，发版时把 latest.json 一起传上去，
URL 就永不变）→ 比对版本 → 下载 → 校验 size+sha256 → `tar.exe` 解压（Win10+ 自带
bsdtar 认 zip，**不引 zip crate**）→ 把当前 exe 复制到 `%TEMP%` 当助手 → 主进程退出 →
助手 `OpenProcess` 轮询 PID 确认旧进程真退出 → 覆盖 → 拉起新版。

**三个必须记住的坑**：
1. **必须等进程真退出，不能 sleep**。`onnxruntime.dll` 被主进程加载着，没退干净就覆盖
   会 `ERROR_SHARING_VIOLATION`，目录停在半新半旧 —— 最难救的一种失败状态。
2. **助手必须在 `tauri::Builder` 之前分流**。它和主程序是同一个 exe，单实例插件会把它
   当成「用户又双击了一次」踢掉，表现为「点了更新，程序关掉再也没起来」。
3. **latest.json 必须无 BOM**。serde_json 遇 BOM 直接 `expected value at line 1 column 1`，
   而客户端每次启动都读它 —— 带 BOM 等于让所有人更新检查永久报错。
   （`ConvertTo-Json` + `[Text.UTF8Encoding]::new($false)` 写，别用 `Out-File`。）

版本比较用 `version.rs::cmp_version`，**数值比不是字符串比**：
`"0.10.0" < "0.9.0"` 在字典序上成立，这么比会漏更新——最典型的一类更新器 bug。

### 发版脚本 `scripts/release.ps1`
一条命令：编译 → 打包 → tag → 上传 zip + latest.json → 打印自检清单。
先拦三种发版事故：**工作区未提交 / tag 已存在 / 产物缺失**。
`-Draft` 发草稿（不占 latest 指针）、`-SkipBuild` 只重传。
